# Chrome 免登录调试浏览器技能 — 原理说明

## 为什么要做这个

AI Agent（小蓝）在操控国内平台时面临三个核心问题：
1. **反爬虫机制** — 抖音、小红书、今日头条等平台会检测非浏览器流量，直接请求 API 或使用 Puppeteer/Selenium 会被 ban
2. **验证码/扫码登录** — 每次需要登录时都要用户手动扫码，完全无法自动化
3. **登录态短暂** — 用 API Key 或 Token 的方案，过期后需要重新获取

## 解决思路

「不绕开验证码，直接绕过验证码的出现场景。」

### 传统方案 vs 本方案

| 传统方案 | 问题 | 本方案 |
|---------|------|-------|
| Selenium/Puppeteer 无头浏览器 | 容易被检测为机器人 | 使用真实 Chrome 实例（非无头） |
| API 接口直调 | 需要破解加密参数 | 完全不用破解，真实浏览器行为 |
| Cookie 导出导入 | Cookie 可能绑定 IP/MAC 地址，导出后失效 | 保留在 Chrome 原生 Cookie 存储中 |
| 代理池切换 IP | 成本高、不稳定 | 一次登录，永久有效 |

## 核心原理

### 1. Chrome 调试端口（CDP）

Chrome 原生支持远程调试协议（Chrome DevTools Protocol），通过 `--remote-debugging-port` 参数启动后，Chrome 会在本地监听一个 HTTP + WebSocket 端口。

Agent 可以通过这个端口：
- 查看所有已打开的标签页
- 打开/关闭标签页
- 获取所有 Cookie（包括 httponly 的）
- 执行任意 JavaScript（相当于在控制台里跑代码）
- 模拟点击、填表、滚动等用户操作

### 2. 独立用户数据目录

```bash
--user-data-dir="C:\Users\李清杰\AppData\Local\Google\Chrome\小蓝调试"
```

这个参数让 Chrome 使用一个**完全独立**的配置文件目录，包含：
- **Cookies** — 存在 `Default/Cookies`（SQLite 数据库文件），关闭 Chrome 不会丢失
- **Local Storage** — 网站的本地存储数据
- **登录凭据** — `Default/Login Data`
- **扩展程序、缓存、历史记录**

与用户的主 Chrome 完全隔离，互不影响。

### 3. 一次登录 + 永久持久化

```
用户手动登录 → Cookie 写入 SQLite → Chrome 关闭 → 磁盘持久化
→ Chrome 重启 → 从 SQLite 加载 Cookie → 自动登录 → Agent 直接使用
```

关键区别：传统方案中，Agent 通过代码自动登录，需要破解验证码。本方案中「登录」这个动作由人类完成一次，之后 Agent 永远不需要再登录。

### 4. --remote-allow-origins 的必要性

Chrome 128+ 版本新增了安全限制：默认拒绝来自不同 Origin 的 WebSocket 连接。如果不加这个参数，Python/Node.js 的 WebSocket 客户端连接 CDP 时会被返回 403。

## 已登录平台及凭证

| 平台 | Cookie 关键字段 | 持久化位置 |
|------|----------------|-----------|
| 抖音 | passport_csrf_token, sessionid | 小蓝调试/Default/Cookies |
| 今日头条 | sessionid, csrftoken | 同上 |
| 小红书 | web_session, id_token | 同上 |
| 站酷 | psid | 同上 |

## 为什么这个方案比其他方案好

1. **零破解成本** — 不需要逆向抖音/小红书的加密参数
2. **零维护成本** — 不需要维护代理池、打码平台
3. **人类级指纹** — 使用真实 Chrome 的 TLS 指纹、Canvas 指纹、UserAgent
4. **长期稳定** — 只要 Chrome 版本不大改 Cookie 加密方式，永久有效
5. **扩展性强** — 想增加新平台，在调试浏览器中登录一次即可
