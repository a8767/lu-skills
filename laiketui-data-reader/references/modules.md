# 抖音来客后台模块与字段映射

> 用途：为 `laiketui-data-reader` 提供各数据模块的入口、关键字段与字段标准化映射。
> 注意：来客后台 URL 与导航文案会随版本变化。以下为 2025–2026 常见形态，实际以 `browser-use state` / `screenshot` 确认的页面为准。

## 1. 登录入口（先确认）
- 主入口（PC 商家后台）：`https://life.douyin.com/p/login`
- 核销数据备用域名：`https://laike.douyin.com`（部分账号/旧版）
- 登录方式：手机号验证码 / 主账号扫码（**不可自动化输入**，须复用用户 Chrome 登录态）

## 2. 顶部导航 / 模块地图
登录后常见导航：首页 · 门店管理 · 团购管理（团购商品）· 营销中心 · 数据中心（生意经）· 订单 · 评价管理。
部分账号把"数据中心"细分为：流量、成交、核销、退款、复购、人货场、门店排名、效果归因。

## 2.5 实战版：生意经数据中心（life-data.cn，已实测跑通）
> 商家真正的经营分析在**独立域名 `life-data.cn` 的「生意经官方数据平台」**，从 `life.douyin.com` 顶部导航「生意经」进入会跳转过去。
> 门店管理员账号进入后有**商户选择弹窗**，需搜索/选中目标商户（如「青石峡漂流」）才能进该商户数据中心。以下为实测的真实模块结构与字段。

### 2.5.0 四维度复盘的周期与日期范围
数据中心的"自定义"日历按以下范围设定（边界由 `scripts/aggregate.py period` 统一计算，避免手工算错）：

| 复盘类型 | key 形式 | 时间窗（示例） | 说明 |
|----------|----------|----------------|------|
| 周 `week` | `week/YYYY-MM-DD` | 上周一~上周日（07/06~07/12） | 自然周（周一至周日） |
| 月 `month` | `month/YYYY-MM` | 上月 1 日~月末（06/01~06/30） | 自然月 |
| 季 `quarter` | `quarter/YYYY-Qn` | 上季首月 1 日~末月末（Q2: 04/01~06/30） | 自然季 Q1=1~3月… |
| 年 `year` | `year/YYYY` | 上年 1/1~12/31（2025-01-01~12-31） | 自然年 |

> `--completed` 语义：取"上一完整周期"；不传则取含参考日的当期。

> ⚠️ **日期范围 UI 实测限制与推荐路径（关键，2026-08-06 更新）**：
> 生意经数据中心日期选择规则已由用户截图明确为一套决策树（详见 `references/user-taught-methods.md` 方法八）：
> - **月度复盘**：优先点「自然月」→ 选目标月份，自动锁定当月 1 日~月末。
> - **周复盘**：仅当今天是**周一**时，可直接点「近7天」= 上周完整自然周；**周二~周日禁止用「近7天」**，会混入本周数据，必须走「自定义」手动选上周一~上周日。
> - **特殊/跨月/非标准周期**：没有对应快捷按钮时，点「自定义」→ 双月面板选起止日（跨月先起点、再点终点）。
>
> 自动化层面：2026-08-01 已通过 **React fiber `props.onClick`** 法打通 `byted-date` 新版自定义日历（点日格对合成事件无响应，fiber onClick 才生效），不再需要用户手动设日期。若 fiber 法失败，按方法三人机补位约定请用户手动设好后 agent 续读。

### 2.5.1 经营概览（经营标签）
- 成交金额（GMV）
- 核销金额
- 退款金额
- 预约金额
- 成交/核销券数（需点进「交易查询」或概览详情才显示）

### 2.5.2 流量（流量标签）
- 线上曝光次数（总）
- 门店页访问人数
- **流量来源表**（按来源拆分，每行含）：
  - 直播：直播间曝光人数、直播成交金额、直播核销金额、直播转化率
  - 视频（短视频）：视频曝光、视频成交金额、视频核销金额
  - 搜索：搜索曝光人数、搜索成交金额、搜索核销金额、搜索转化率

### 2.5.3 内容分析（内容标签，含直播/视频明细）
- **直播分析**：直播间成交金额、直播核销金额、直播退款金额、**直播时长（秒，需 ÷3600 换算小时）**、**直播场次数**、直播间曝光人数、直播间观看人数、曝光→成交转化率、观看→成交转化率
- **视频分析**：短视频成交金额、视频播放量、**种草价值**、视频成交券数、视频转化率

### 2.5.4 人群资产（人群标签）
- 新客成交数 / 老客成交数
- 复购人数 / 复购率（近7天）
- 人群画像：年龄分布、性别、城市层级、消费力标签（如"24-40岁中高消费力精致妈妈"）

### 2.5.5 评论/评价
- 新增好评数、新增中差评数（入口可能在「评价管理」或内容/人群模块，按页面实际定位）

- 退款数/退款 → refund_count

## 5. 取值健康参考（用于复盘解读，非强制）
- 核销率：团购类目建议 ≥ 60%，低于 40% 需复盘
- 退款率：建议 ≤ 10%
- 待核销金额：低于总销售额 40% 为健康
- 新客占比：团购活动建议 ≥ 30%
- 分析周期：以 7 天为单位横向对比，避免单看某一天

## 7. 四维度复盘：四类数据字段映射

任意复盘（周/月/季/年）都必须覆盖下面**四类数据**，缺一类即不完整。统一数据模型见 `review-schema.md`。

### 7.1 统计数据（stats）
即本周期从生意经各模块抓取的核心指标（=第 2.5 节全部字段），其英文键见 `review-schema.md` 第 6 节指标全集（gmv / verified_amount / coupon_sold / exposure / live_gmv / video_views / search_gmv / new_customers / repurchase_rate / good_reviews …）。

### 7.2 对比数据（comparison）
| 子类 | 对照周期 | 生意经取数位置 | 指标键后缀 |
|------|----------|----------------|------------|
| 环比 `qoq` | 上一相邻周期 | 开启页面「对比」开关 → 读"较上一周期"delta | `_qoq_pct` |
| 同比 `yoy` | 去年同期 | 开启页面「对比」开关 → 读"较去年同期"delta | `_yoy_pct` |

> 若页面未直接给 delta，`aggregate.py review` 会从已存的上一周期/去年同周期记录自动计算环比/同比，无需重复抓取。

### 7.3 趋势分析（trend）
| 复盘类型 | 趋势粒度 | 默认子周期数 N |
|----------|----------|----------------|
| 周复盘 | 周 | 8 周 |
| 月复盘 | 月 | 12 个月 |
| 季复盘 | 季 | 8 季 |
| 年复盘 | 年 | 5 年 |

取数：把日期范围拉到对应长窗口，读取逐子周期的同一指标序列（或由历史多条记录拼接）。序列最末点 = 当前复盘周期。

### 7.4 目标完成度（goal）
- 目标值来源：`config/targets.json`（按 `客户 → 周期类型 → 指标键` 配置），由运营维护。
- 完成率 = 实际值 / 目标值 × 100%。
- 未配置目标的指标完成率标记"未设目标"。

## 8. 复盘模板扩展到月 / 季 / 年

周复盘模板的字段（见第 6 节）在月/季/年复盘中**字段完全相同**，仅时间窗放大、且额外补充四类数据：

| 维度 | 时间窗 | 在周模板基础上增加的输出 |
|------|--------|--------------------------|
| 周复盘 | 上周 | 基础模板字段 |
| 月复盘 | 上月 | + 环比( vs 上月) / 同比( vs 去年同月) / 12个月趋势 / 月度目标完成度 |
| 季复盘 | 上季 | + 环比( vs 上季) / 同比( vs 去年同季) / 8季趋势 / 季度目标完成度 |
| 年复盘 | 上年 | + 环比( vs 前年) / 同比( vs 前年) / 5年趋势 / 年度目标完成度 |

**话术模板（月/季/年可直接套用，把"周"换为对应周期，并附对比/趋势/目标三节）：**
```
哈喽各位老板，以下是门店【<周期，如 2026年6月>】整体数据复盘

【成交数据】成交GMV / 核销金额 / 成交券数 / 核销券数
【对比数据】环比（vs 上一<周期>）GMV ±x% / 核销 ±x%；同比（vs 去年同<周期>）GMV ±x%
【人群数据】新客/老客成交数、复购率、主要客群画像
【流量数据】线上曝光、直播(成交/核销/时长/场次)、视频(成交/播放/种草)、搜索(成交/核销/曝光)
【趋势分析】近 N 个<子周期> GMV / 核销走势
【目标完成度】GMV 实际/目标 = x%（未设目标则略）
【评论数据】新增好评 / 中差评
以上数据请您查收~
```
> 月/季/年复盘建议把"同比""趋势""目标完成度"单独成节，比周复盘信息密度更高，便于老板看长期走势与年度目标进度。

## 9. 抖音林客 → 商家数据 → 商家列表（代运营商家全量采集，**2026-08-15 实测跑通**）

> **用途**：服务商 / 代运营公司视角，**一次性拉出旗下全部代运营商家在某时间窗的核心指标**，用于代运营对账、商家健康度巡检、补贴/佣金成本测算。
> **与「生意经」(life-data.cn) 的区别**：林客看的是**服务商后台跨商家汇总**，单商家经营详情仍需进各商家的生意经；这里我们只做"代运营全量 + 跨商家对比 + 推广成本测算"。

### 9.1 入口与导航（**实测**，注意与截图差异）
```
抖音林客 (life-partner.cn)
  → 左侧菜单「商家数据」
    → 顶部 Tab「商家列表」（截图里写的"探索列表"在本账号实为「商家列表」；
       同排还有「商家概览 / 商家分析 / 商家列表」三个 tab）
      → 表格列出全部代运营商家
```
- 子 tab（筛选）：`全部商家 / 服务中商家 / 无动销商家 / 新签商家 / 取消合作商家`（**注意：没有"无忧核"，是"无动销"**）
- 时间预设（实测存在）：`今日实时 / 近1天 / 近7天 / 近30天 / 本月 / 自定义`。**「本月」= 自然月至今（可靠，已用）**；`近1个月` 是 30 天滚动窗。

### 9.2 字段定义（表格列，14 列，**div 结构非原生 table**）

| 表格列 | 标准字段 | 单位 | 用户关注 |
|--------|----------|------|----------|
| 商家名称（含「商家ID: 72...」附注） | `merchant_name` + `merchant_id` | - | ✓ |
| 行业 | `industry` | - | |
| 合作模式 | `cooperation_mode` | - | |
| 类目 | `category` | - | |
| 跟进人 | `follower` | - | 多人逗号分隔 |
| 商家经营分 | `business_score` | 分（浮点） | |
| 支付GMV | `pay_gmv` | 元 / 万元 | ✓（= 成交GMV） |
| 核销GMV | `verified_gmv` | 元 / 万元 | **✓ 核销关注数据成交GMV** |
| 退款GMV | `refund_gmv` | 元 / 万元 | ✓ |
| 视频直接支付GMV | `video_pay_gmv` | 元 / 万元 | **实测列名如此（非"核销医美支付GMV"）** |
| 直播支付GMV | `live_pay_gmv` | 元 / 万元 | |
| 总预估佣金 | `total_est_commission` | 元 | **✓** |
| 服务商预估佣金 | `provider_est_commission` | 元 | **✓** |

> **DOM 结构（关键）**：本表是 **div 模拟表格**，class 前缀 `lifep-table`（不是 `<table>/<thead>`）。
> 表头=`.lifep-table-header-content-title`；数据行=`.lifep-table-row`（排除含 `header-title` 的表头行）；单元格=`.lifep-table-cell`。
> 脚本据此定位，不要再用 `document.querySelectorAll('table')`。

### 9.3 衍生计算（脚本自动算）
| 衍生字段 | 公式 | 用途 |
|----------|------|------|
| `verify_rate` | 核销GMV / 支付GMV | 单商家核销健康度 |
| `refund_rate` | 退款GMV / 支付GMV | 单商家退款健康度 |
| `promotion_cost` | **总预估佣金 - 服务商预估佣金** | **服务商推广支出佣金成本**（用户原话："两个预估佣金的差值就是服务商推广支出佣金的成本"） |

> 解析规则：表格里 `¥128.05万 / 8,261元 / 70.13万` 都自动识别为元（浮点），已知踩坑过的单位只有「万 / 亿 / 元 / ¥」。

### 9.7 已知踩坑 / 实测笔记
- **表格是 div 不是 `<table>`**：`get_table_headers`/`get_table_rows` 旧版用 `querySelectorAll('table')` 会返回空 → 已改为 `.lifep-table-*` 选择器（见 `extract_daiyunying.py`）。
- **`ld.eval` 包裹陷阱（致命）**：`ld.eval` 会把表达式包进 `(function(){ EXPR })()`。如果 EXPR 是**裸 IIFE** `(function(){...})()`，外层函数把它当语句执行、**返回值被丢弃 → 永远得到 undefined**。凡是 `eval` 需要返回值的表达式，必须自带 `return`（如 `return (function(){...})()`）或是裸表达式。`click_next`/`get_headers`/`get_rows` 都因此改过。
- **翻页陈旧数据**：点下一页后不能立刻读，要轮询首行商家变化；且开跑先点回第 1 页。
- **时间口径**：林客「近1个月」≠ 自然月；"本月"用「本月」预设最稳。服务商两列佣金是"应付总额"和"应付给服务商的部分"，差值=推广支出，与「生意经→投放分析」口径不完全一致，报告需注明来源。
- **退款GMV 偏高**：实测整体退款GMV(¥359.6万) > 核销GMV(¥320.6万)，且二者之和大于支付GMV，说明退款口径可能含跨期/全额退款，勿直接相减，建议结合单商家生意经核对。
- **测试状态**：2026-08-15 **已在真实林客登录态端到端跑通**，成功采集 85 家全部商家、两列佣金均捕获，输出 CSV/JSON + 衍生率值与推广成本。

### 9.8 与「6/7 节（生意经复盘模板）」的关系
- 9 节（林客列表） = **跨商家横向对比 + 服务商成本测算**
- 6/7 节（生意经单商家）= **单商家纵向深度复盘（含趋势/同比/目标）**
- **典型组合用法**：先跑 9 节拿全量列表筛选「核销率 < 40% / 推广成本 > X / 经营分低」的商家 → 再针对这些商家跑 6/7 节的四维度复盘。
